```
员工 → 网关登录页 → 钉钉 / 飞书 / 企业微信 识别身份
                     ↓ 按平台 ID（→ 手机号兜底）匹配员工
                     网关用员工的原系统账号密码代登录原系统
                     ↓ 把原系统会话 Cookie 种到网关地址
                 → 反向代理进入原系统，员工全程无感
```

原系统**不需要改一行代码**：对浏览器来说，原系统就挂在网关域名下面。

## 一、快速启动

1. 双击 `启动.bat`（或命令行 `sso3.exe`）。
2. 打开管理后台 [http://本机IP:50/admin](http://本机IP:50/admin)，默认账号 `admin` / `admin123`（登录后请立刻改）。
3. 三个标签页按顺序配：


| 标签页       | 配什么                                                     |
| --------- | ------------------------------------------------------- |
| **第三方登录** | 钉钉 / 飞书 / 企业微信的应用凭据 + 运行信息（入口地址、缓存状态）                   |
| **应用管理**  | 应用列表（绑定域名 → 转发目标，最多 9 个域名/应用）、登录接口与 Cookie 转发（按应用）、网关自身 |
| **用户管理**  | 员工映射：平台身份 ↔ 原系统账号密码（支持批量导入）                             |


配好后把「运行信息」里的入口地址发给员工，或填到各平台工作台的应用首页。

### 端口


| 端口    | 用途             | 配置项            |
| ----- | -------------- | -------------- |
| `:50` | 管理后台（`/admin`） | `admin_addr`   |
| `:55` | 员工登录 + 反向代理    | `gateway_addr` |

## 二、员工入口


| 入口                 | 说明                              |
| ------------------ | ------------------------------- |
| `/niu/login`       | 选择页：三个平台按钮 + 原系统账号密码            |
| `/niu/dingtalk`    | 钉钉免登入口，同时是回调地址                  |
| `/niu/feishu`      | 飞书免登入口，同时是回调地址                  |
| `/niu/weixin`      | 企业微信免登入口，同时是回调地址                |
| `/niu/<平台>?diag=1` | 只排查身份、不登录：把这次拿到的平台 ID / 手机号摊开显示 |
| `/niu/dev`         | 调试免登（仅内网，需 `dev_login: true`）   |


`/niu/*` 是网关私有命名空间，不会被转发给原系统。

### 各平台怎么最省事

- **钉钉**：客户端内走 authCode **零点击免登**（需要填 CorpId）；浏览器打开跳授权页扫码。
- **飞书**：客户端内 JSAPI 静默取码；浏览器跳授权页（授权过的账号直接回跳）。
- **企业微信**：客户端内 `snsapi_base` **全静默**；浏览器跳扫码登录页。

## 三、员工映射与匹配顺序

一个员工一行，可以同时绑三种身份，任一端登录都进**同一个原系统账号**。

```
钉钉 userId / unionId  ┐
飞书 open_id / union_id ├─→ 命中即登录
企微 userid / openid   ┘
        ↓ 都没命中
    手机号（三平台通用兜底）
```

- 平台 ID 是授权时直接返回的，最稳；手机号需要平台额外授权，作为兜底。
- 手机号命中后会**自动回写**平台 ID（只填空字段，不覆盖已有绑定），下次直接按 ID 走。
- 匹配走内存缓存（四个索引），管理员增删改员工**立即生效**，另有 60 秒兜底刷新。

### 批量导入

「用户管理 → 批量导入」，两种格式（逗号 / 制表符 / 空格分隔均可）：

```
# ① 平台模式
平台,标识,姓名,原系统账号,密码[,手机号]
dingtalk,manager1234,张三,zhangsan,Abc@12345,13800138000
feishu,ou_abc123,李四,lisi,Abc@12346

# ② 手机号模式（首列是纯数字手机号）
13900139000,王五,wangwu,Abc@12347
```

平台填 `dingtalk` / `feishu` / `wecom`。已存在的记录更新账号和姓名，密码留空保持原密码。

### 为什么没有「先建人再绑身份」这一层

因为平台身份本身不保证稳定：手机号会变、员工会换部门、外部联系人有 openid 没 userid。  
网关的做法是「**能拿到什么就用什么匹配，匹配成功后立刻把拿到的都补进员工表**」——  
第一次可能靠手机号进来，之后就一直靠平台 ID，越来越快也越来越稳。

## 五、应用管理（多系统转发）

管理后台「**应用管理**」标签页，以应用为单位管理转发：一个网关可以同时转发多个系统，按请求的**域名（Host）**&amp;#x628A;流量送到对应系统。


| 概念           | 说明                                                                      |
| ------------ | ----------------------------------------------------------------------- |
| 应用           | 一段「绑定域名 → 转发目标」的配置；员工用绑定的域名（解析到网关转发端口）访问该应用                             |
| 绑定域名 / IP    | 每个应用最多 **9** 个，每行一个；支持填 IP（如 `10.11.2.5`），按 Host 归一匹配（忽略大小写与端口）         |
| 默认应用         | 绑定 `0.0.0.0` 或**不绑定任何域名**的应用：所有地址都可以访问，并兜底未命中任何域名的请求（默认行为，升级老配置自动迁移出一个） |
| 转发目标         | 最终服务端的协议 + 主机（IP 或域名）+ 端口 + 单次转发超时                                      |
| 登录接口配置       | 登录路径、POST 数据模板、成功 / 失败标识、Content-Type、超时、附加请求头——每个应用独立                  |
| 会话 Cookie 转发 | 要转发的 Cookie 名（留空=全部）、Domain（留空=种到网关当前地址）、Path——每个应用独立                   |
| 第三方登录（应用级）   | 操作列「钉钉 / 飞书 / 企业微信」三个按钮：每个应用可以绑定**自己的**三方应用凭据，独立决定是否启用                  |


匹配顺序：**先精确命中绑定域名/IP（先创建的优先），再回退默认应用**；Host 没命中任何绑定域名、又没有默认应用时，整个端口对该地址一律 404（登录页、转发都不给）——「只绑定某个域名」真正起约束作用。

**应用级第三方登录**：「应用管理 → 操作」里的**钉钉配置 / 飞书配置 / 企业微信配置**，点开单独填凭据、独立启用开关：

- 应用**单独配置了凭据**（任意一项非空）→ 登录页用应用自己的配置，与全局互不影响；
- 应用**没配置** → 回落到「第三方登录」标签页里的全局配置（老部署不用改任何东西）；
- 同一份全局配置也可以多个应用共用，登录页平台按钮按「当前访问域名所属应用」动态显示。

一个应用的例子：绑定 `oa.example.com`，转发到 `http://10.11.0.51:8080`，登录接口 `/v1/login`，模板 `{"username":"{{username}}","password":"{{password}}"}`，成功标识 `"code":0`——员工用 `oa.example.com` 打开系统，钉钉/飞书/企微免登或密码登录后由网关代登录原系统，全程无感。

占位符：`{{username}}` `{{password}}` `{{phone}}` `{{name}}`。

## 五.1、应用防火墙（登录前拦截）

管理后台「第三方登录 → 网关自身」里的**登录前拦截访问**开关，打开后转发应用就多了一道前置门槛：


| 访问                                    | 结果                                               |
| ------------------------------------- | ------------------------------------------------ |
| `WW_verify_*.txt` / `MP_verify_*.txt` | 永远放行（平台域名校验要抓）                                   |
| `/niu/*`（登录页、三个平台免登入口、登录接口）           | 永远放行                                             |
| 其余路径，**没有会话**                         | 页面 → 302 到 `/niu/login?next=<原地址>`；接口 → 401 JSON |
| 其余路径，**有会话**                          | 照旧转发给原系统                                         |


默认关闭，升级后不会突然把所有人挡在门外。打开时后台会检查：三个平台至少要启用一个，或保留「允许账号密码直登」，否则拒绝保存（免得把自己锁在外面）。

判定「有会话」看两样，任一命中即放行：

1. `niu_s` 标记有效：HMAC 签名正确，且标记里记的原系统会话 Cookie 名/值指纹与本次请求完全对得上；
2. 请求里带着后台配置的「要转发的 Cookie 名」（如 token）且值不为空。

第 2 条是必须的兜底：标记会随登录态过期（默认跟随 `jwt_expires`），但原系统会话常常还活着，只认标记会把正常登录的人弹回登录页。原系统退出登录删掉 Cookie 后，两条都不成立，立刻重新拦截。

这层挡的是**匿名访问**（扫描器、外部人员、没登录就直接打开的深链接），不是替代原系统鉴权：会话是否真的有效仍由原系统判定。

被拦下来的深链接会通过 `next` 一路带过 OAuth，登录成功后回到原页面；`next` 只接受站内相对路径，`//evil.com`、`http://…`、`/\evil.com` 一律丢弃。

## 五.2、IP 黑白名单

管理后台&amp;#x7684;**「白名单」与「黑名单」**&amp;#x4E24;个标签页（分开管理），按来源 IP 再分一层。规则存 `sso_ip_rule` 表，启动时预加载成内存快照，请求路径上只做内存比对。


| 来源          | 结果                                                               |
| ----------- | ---------------------------------------------------------------- |
| 黑名单（IP 或网段） | 转发端口对**任何地址**都返回 `web/404.html`（状态 404），对外表现和「页面不存在」一样，不暴露被拉黑的信号 |
| 白名单         | 直接放行到原系统，**不再弹登录页**（原系统自己判会话）                                    |
| 都不命中        | 走正常流程；验证失败累计到阈值 → 自动进黑名单                                         |


**这个开关只管转发端口**。管理端口**[http://127.0.0.1:50&amp;#x20](http://127.0.0.1:50&#x20);**&amp;#x523B;意不做任何限制——否则一旦把自己的 IP 拉黑，后台都进不去，只能改数据库救回来。

两个标签页各管各的：

- **白名单页**：「验证通过自动加白」开关（与总开关无关，关着也会记录）、白名单列表；顶部实时显示「最近自动加白」的 IP 和时间，登录后没进白名单时一眼能看出问题。手工添加时可选**有效期（天）**：留空 / 0 = 永久，填 N 天则到期自动移除（列表里能看到到期时间与「已过期」标记）。
- **黑名单页**：总开关 + 判定参数 + 黑名单列表（可添加 / 解封）。

判定参数（黑名单页里改）：


| 参数       | 默认    | 说明                                      |
| -------- | ----- | --------------------------------------- |
| 自动拉黑阈值   | 10 次  | 同一 IP 在窗口内失败多少次就进黑名单                    |
| 计数窗口     | 10 分钟 | 超过窗口重新计数，隔天的零散误输不会累成一条命                 |
| 验证通过自动加白 | 开     | 在白名单页设置；登录验证通过的 IP 写入白名单（`source=auto`） |
| 自动拉黑时长   | 24 小时 | 只作用于自动拉黑；**手工加入的黑名单不会自动过期**，要手动解封       |


什么算「验证未通过」（达到阈值自动拉黑）：

1. 登录页账号密码错误；
2. 钉钉 / 飞书 / 企业微信**验证不通过**——授权码无效或过期、换令牌失败、平台身份匹配不上员工（拿着私人账号反复试同样会计）；
3. 未登录访问受保护页面被拦（仅登录前拦截开启时）；
4. 代登录原系统失败。

不计的：管理员配置类错误（平台未启用、AppKey 没填、应用没发布、企微 60020 可信 IP 未配等）——那是管理员的问题，不该封员工 IP。

**黑名单优先**：同一个 IP 同时在两份名单里，按黑名单拦截——管理员明确拉黑是明确的管理动作，白名单不能盖掉它。加入黑名单时会自动把同 IP 移出白名单。注意：自动拉黑的出口 IP（如办公网大出口）即使随后有人登录成功也不会被白名单放行，需管理员到「黑名单」页解封或等自动拉黑到期；白名单 IP 依旧不累计失败次数。

其它细节：

- 支持单个 IP 与网段（`192.168.1.10`、`192.168.1.0/24`），输入按行/逗号拆分，可一次加多条；`192.168.1.5/24` 会归一到 `192.168.1.0/24`。
- 加白名单时会顺手删掉同 IP 的黑名单记录；而给白名单里的 IP 加黑会被拒绝并提示先移除白名单（避免界面自相矛盾）。
- 解封会同时清零该 IP 的失败计数，不会「刚解封又立刻触顶」。
- 后台每张卡片顶部给出「正在累计失败」的 IP 列表，可以在被封之前先看到苗头。
- 过期清理与快照重建由后台协程每分钟做一次（多实例部署、或有人直接改库，也能在一分钟内对齐）。

> 来源 IP 取自 `X-Forwarded-For` 第一个地址，没有该头时用 TCP 对端地址。网关前面有 nginx 之类的反代时这是必要的；如果网关直接暴露在公网，建议在反代层清洗这个头，否则对方可以伪造来源。

## 五.3、蜜罐端口（端口管理）

后&amp;#x53F0;**「端口管理」**&amp;#x6807;签页：在网关上额外开一批**假端口**。真实业务一个都不用这些端口，正常员工也永远不会连它们，所以「连上就记一笔」几乎不会误伤自己人；扫描器 / 攻击者顺着端口号去试，撞够次数就进黑名单。

- **端口写法**：单个 `3389`、连续范围 `1-9999`（也支持 `1~9999`）、逗号或空格分隔的组合 `22,80,3306,8000-8100`。单条上限 10000 个端口，所有启用条目合计上限 20000 个。
- **不会硬抢端口**：网关自己的端口（管理端 `/` 转发端）永不参与；被别的程序占用的端口绑不上也不会报错，列表里显示「没绑上 N 个」并列出端口号，等它释放后点「重新监听」即可。
- **判定参数**（页面里改，保存即重绑）：


| 参数        | 默认       | 说明                             |
| --------- | -------- | ------------------------------ |
| 达到阈值自动拉黑  | 开        | 关掉 = 观察模式：只记录命中，不拉黑            |
| 命中阈值      | 5 次      | 同一 IP 在窗口内连上假端口多少次就拉黑          |
| 计数窗口      | 10 分钟    | 超过窗口重新计数                       |
| 拉黑方式      | 临时 24 小时 | 可选**永久**（需手工解封）；临时到期自动解封       |
| 回应方式      | 假指纹后断开   | 也可「假指纹 + 挂住连接」（拖住扫描器时间）或「立即断开」 |
| 单 IP 并发上限 | 8        | 超过就丢掉它的连接，防止把网关耗死              |


- **假指纹**：按端口回一条像真服务的 banner（22 → OpenSSH、21 → vsFTPd、25 → Postfix、3306 → MySQL 握手包、6379 → Redis 认证提示、3389 → RDP 协商应答、80/443/8080 等 → nginx 响应头），未知端口不回内容。
- **拉黑写进同一张 `sso_ip_rule` 表**（`source=honey`），所以黑名单页能直接看到、手工解封；判定上按**自动黑名单**处理（会过期、被**永久白名单**压过——分公司出口那种大 IP 不会被蜜罐连累）。
- 拦截**不看「IP 黑白名单」总开关**：蜜罐自己认定是扫描的，记了黑名单就一定在转发端口生效（返回 404），不会出现「记了却不生效」。
- **不写爆数据库**：命中按 IP 节流（同一 IP 5 秒一条），被拉黑时必记一条；日志只留最近 3000 条；端口累计命中数在内存里累加、每 30 秒回写一次。
- TOP 20 榜单按命中次数排，标出哪些 IP 已被拉黑，可以一键解封（只删蜜罐拉黑的那条，手工黑名单不动）。

> 端口越多越像一台真机器，但也越吃文件句柄。别一上来就 `1-9999`：挑几段「看起来该有服务」的（如 `21-23,25,3306,3389,6379,8080`）通常就够引鱼上钩了。

## 五.4、连接池管理

后&amp;#x53F0;**「连接池」**&amp;#x6807;签页，实时观察转发端口上「正在连接」的来源 IP。

- 记录内容：IP、请求数、首次 / 最近活跃时间、空闲时长、最近一次的 User-Agent。
- 「正在连接」的定义：最近活跃在**活跃窗口**内（默认 5 分钟，页面上可改，1 – 1440 分钟）；超过窗口没动静的 IP 自动移出。
- 表格本身是纯内存滚动记录，**不落库**——它回答的是「现在谁正连着」，不是访问日志，重启后从零开始。要留证据请用下面的「访问日志」。
- 记录点在转发端口所有请求的最前面，所以**被登录前拦截、被黑名单挡掉的请求也会出现**——扫描器一来就能看见（典型如盯着 `/.env`、`/admin.php` 的 `python-requests`）。
- 状态列显示该 IP 当前的黑白名单归属，未登记的可以**一键加白 / 拉黑**（写的就是黑白名单接口，加完立即生效）。
- **用户列**：登录成功（密码直登或钉钉 / 飞书 / 企业微信免登）时把「这个 IP 上是谁」记进连接池——原系统登录名 + 员工姓名 + 登录方式 + 次数 + 时间；同一 IP 多个用户各占一行，共用出口时一眼看出都有谁在用。只看请求、没登录过的 IP 用户列为「—」。
- 可选「自动刷新（5 秒）」持续观察；切到别的标签页会自动停止轮询。
- 上限 5000 个来源，超过时先清过期的、仍满就不再记录新来源，防止恶意流量把内存打爆；正常业务到不了这个量级。

### 访问日志（落库）

页面下半部分的「访问日志」把每条请求单独记一行到 `sso_conn_log`，重启不丢：

- 一行记什么：**时间、来源 IP、端口（本机监听口 / 客户端源端口）、连接数、请求数、用户、请求客户端、请求数据**。连接数与请求数取的是记录那一刻该 IP 的值，和上表同一口径，两边数字对得上。
- **请求数据自动识别**：GET / HEAD 记 query；POST / PUT / PATCH / DELETE 等带 body 的方法按 Content-Type 认成「表单 / JSON / 上传 / 原始」，表单和 JSON 里的密码、token、secret 类字段一律打成 `***`，上传只记文件数与总体积（不读内容）；超长截断到 500 字节。
- 日志卡片顶上分**两个维度**筛：**方法**（GET / POST / PUT / PATCH / DELETE / HEAD / OPTIONS / 其他）和**数据形态**（表单 / JSON / 上传 / 原始）。方法对应库里单独一列；形态用模糊匹配，所以选「表单」会把 POST 的表单和 PUT / PATCH 的表单一起筛出来。`其他` = 标准 9 个方法之外（WebDAV 的 PROPFIND / MKCOL、PURGE 等）。
- **请求客户端**存 UA 原文，页面按它显示成「Chrome 141 · Windows」这种短标签（鼠标悬停看原文）。
- 默认**开启**、最多 **9999** 条、**不限**保留天数（页面上可改）。条数上限超出后**循环删除日期最早**的那一批；保留天数与条数上限是两条独立规则，哪个先到按哪个清。条数 / 天数填 `0` 都表示不限制。
- **记录类型可挑**（页面「访问日志」那一行，单独摆在「活跃窗口」上面）：**正常 / 错误 / 白名单 / 黑名单**四个复选框，默认全勾。勾掉的类型**当场就不入队、不入库**，省下的是条数上限和磁盘——只留「错误」的话，9999 条能撑的时间长一个量级。四条互斥，优先级固定为：
  
  | 分类  | 判定                                       |
  | --- | ---------------------------------------- |
  | 黑名单 | 被黑名单 / 蜜罐挡掉的请求（网关回 404 的那些），**不会**混进「错误」 |
  | 错误  | 状态码 ≥ 400：门禁 403、限流 429、上游 5xx、路径不存在 404 |
  | 白名单 | 来源在白名单里、这次正常通过                           |
  | 正常  | 其余                                       |
  

  优先级是「黑名单 &gt; 错误 &gt; 白名单 &gt; 正常」：白名单来源出错时仍记「错误」（勾「错误」才不会漏），黑名单挡掉的 404 记「黑名单」而不是「错误」（否则错误列表会被扫描器噪声灌满）。日志卡片上还有一个「分类」列和对应的筛选下拉，库里的老记录没有分类时显示「—」。
- **改「记录类型」只影响之后的请求，不会回头删已经入库的记录**。所以把「只记错误」保存后，之前记下的正常 / 白名单记录仍然在表里——这不是设置没生效。为了不让人误判，只要表里存在「不在当前记录类型范围内」的记录，日志卡片工具栏下面就会出现一条黄色提示，写清各类的条数、说明它们是改动前入库的；旧记录按条数 / 天数上限自然淘汰，需要立刻清掉则用「导出全部」留档后点「清空日志」。
- 写入方式和名单 / 密钥次数完全一致：**先写内存，每 10 秒批量落库**，请求线程绝不碰数据库（否则会重演「每请求一次写库 → SQLite 写锁被占满 → 全站卡死」）。队列满（8192 条）宁可丢日志也不拖慢转发，丢弃条数显示在日志卡片右上角。
- 打开本页时会先催一次落库，最多等 300 毫秒——所以刚发生的请求不用等满 10 秒；「清空日志」只删记录，不动任何配置。
- **导出全部（CSV）**：工具栏上的「导出全部」把**当前筛选条件下的全部记录**导成 CSV，**不受「最近 200/500/1000 条」限制**；不加筛选就是整张表。文件带 UTF-8 BOM（Excel 双击打开中文不乱码），16 列：ID、时间、分类、来源IP、来源端口、目标端口、连接数、请求数、用户、姓名、请求方法、数据形态、状态码、路径、请求客户端、请求数据。边查边写（chunked），几十万行也不会把服务端内存吃满；URL 加 `format=json` 可换成 JSON（字段名与接口一致，给脚本 / pandas 用）。以 `=` `+` `-` `@` 开头的单元格会加单引号前缀，防止 Excel 当公式执行。
- 表格里的**请求数据只画一行**，**点一下弹窗看全文**：弹窗里把这条记录的字段全摆出来（时间、分类、来源 IP / 端口、目标端口、用户、连接数 / 请求数、状态码、方法、UA 原文），请求数据原文等宽显示、保留换行，可一键复制。

### data 目录为什么会有三个文件

SQLite 开了 WAL（预写日志）模式，运行期是这样的：


| 文件            | 作用                              |
| ------------- | ------------------------------- |
| `sso3.db`     | 主库，表结构 + 已合并的数据                 |
| `sso3.db-wal` | 预写日志，**新写入先落这里**，读的时候与主库合并出最新视图 |
| `sso3.db-shm` | WAL 的共享内存索引，只用于多连接协调，**不含业务数据** |


三个文件是一套，不是数据重复。主库看着只有几 KB、数据全在 `-wal` 里，属正常现象（还没合并）。

什么时候会合回一个文件：

- **Ctrl+C 正常退出**：程序会先合并再关闭，`-wal` / `-shm` 自动消失；
- **直接关窗口 / 任务管理器结束**：改动手上还在 `-wal` 里（**数据不会丢**，下次打开会自动恢复），下次启动时会先合并一次；
- **手动合并**（服务已停止时执行）：

```bash
sso3.exe -checkpoint
# WAL 已合并回主库，data 目录里只保留 sso3.db
```

如果服务还在运行，`-checkpoint` 会因库被占用而报错——先停服务再执行。

### 备份

`data/sso3.db`（连同 `-wal` / `-shm`，或先停服务）＋ `config.json` 就是全部数据。  
**注意**：`config.json` 里的 `crypto_key` 是员工原系统密码的 AES-GCM 密钥，丢了等于所有员工密码作废；`jwt_secret` 丢了所有会话失效（会自动重新生成）。
